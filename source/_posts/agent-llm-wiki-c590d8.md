# LLM Wiki 学习笔记

## 一句话

LLM Wiki 的核心不是“让 LLM 帮我检索资料”，而是“让 LLM 持续维护一个会复利增长的 Markdown 知识库”。

传统 RAG 像是每次考试前临时翻书：LLM 在查询时从原始资料里找片段，再当场拼答案。LLM Wiki 则像是持续写教材：每次读到新资料，LLM 都把它编译进已有 wiki，更新概念、实体、索引、矛盾和结论。下次提问时，LLM 面对的不是一堆散乱资料，而是已经整理过、链接过、修订过的知识结构。

## 核心转向

从一次性回答转向持续维护。

- RAG 的主要动作是“查询时检索”。
- LLM Wiki 的主要动作是“读完后沉淀”。
- 有价值的答案不应该留在聊天记录里，而应该回写成 wiki 页面。
- 知识库的价值来自积累、交叉引用、修订和一致性维护。

这套方法本质上把 LLM 从问答器变成 wiki maintainer。人负责选资料、提问题、判断方向；LLM 负责摘要、归档、链接、更新和巡检。

## 三层架构

### 1. Raw sources

原始资料层，是 source of truth。
- 可以是文章、论文、会议记录、网页剪藏、图片、数据文件。
- 原始资料应该尽量保持不可变。
- LLM 可以读取和引用它，但不应该直接改写它。

### 2. Wiki

LLM 生成和维护的 Markdown 页面层。

- 包含主题页、概念页、实体页、对比页、综合页、来源摘要页。
- 新资料进入时，LLM 不只是新增一个摘要，还要更新已有页面。
- 如果新资料挑战了旧结论，要标记冲突、修正综合判断，或保留争议。

### 3. Schema

约束 LLM 如何维护 wiki 的规则层。

- 对 Codex 来说，可以是 `AGENTS.md`。
- 对 Claude Code 来说，可以是 `CLAUDE.md`。
- 它规定目录结构、命名方式、页面模板、引用格式、ingest 流程、lint 流程。

这个 schema 很关键。没有 schema，LLM 只是聊天；有 schema，LLM 才像一个有纪律的知识库维护者。

## 三个核心操作

### Ingest

把新资料读进 wiki。

理想流程：

1. 读取原始资料。
2. 提炼关键观点、事实、概念和不确定点。
3. 写一页来源摘要。
4. 更新相关主题页、概念页、实体页。
5. 补充双向链接和来源引用。
6. 如果和旧结论冲突，明确标记。
7. 更新 `index.md`。
8. 追加 `log.md`。

卡帕西提到，一个 source 可能会触达 10 到 15 个 wiki 页面。这个点很重要：ingest 不是“放一篇摘要进去”，而是把新资料织入已有知识网络。

### Query

基于 wiki 提问和生成答案。

查询时，LLM 应该先读 `index.md`，再进入相关页面，必要时回到 raw sources 核验。好的回答可以继续沉淀：

- 一个对比表可以变成对比页。
- 一次综合分析可以变成主题页。
- 一个临时发现的连接可以变成新的概念页。
- 一个问题清单可以变成后续研究路线。

这样，提问本身也在扩展知识库，而不是用完即丢。

### Lint

定期体检 wiki。

应该检查：

- 哪些页面互相矛盾。
- 哪些旧结论已经被新资料覆盖。
- 哪些页面没有入链或出链。
- 哪些高频概念还没有独立页面。
- 哪些页面缺少来源。
- 哪些主题值得继续找资料。

这一步对应人类维护知识库最容易放弃的部分：整理、修补、清账。LLM 的价值就在这里，因为它不怕重复维护。

## 两个基础文件

### `index.md`

内容索引，帮助人和 LLM 快速定位知识。

它应该按类别列出页面，每项包含链接和一句话摘要。规模不大时，`index.md` 本身就能替代复杂检索系统。LLM 回答问题前先读索引，再钻到具体页面。

### `log.md`

时间线日志，记录知识库发生过什么。

建议使用稳定格式，例如：

```markdown
## [2026-05-28] ingest | Karpathy LLM Wiki
```

这样可以用简单命令按时间检索最近活动，也方便 LLM 理解最近做过哪些 ingest、query 和 lint。

## 和 Obsidian 的关系

Obsidian 适合作为 LLM Wiki 的 IDE。

- Markdown 文件就是代码。
- Wiki 页面就是模块。
- 双向链接就是依赖关系。
- Graph view 可以观察知识结构。
- Git 可以提供版本历史。
- Dataview 可以基于 frontmatter 做动态索引。

卡帕西的比喻很贴切：Obsidian 是 IDE，LLM 是 programmer，wiki 是 codebase。

## 我对这套方法的理解

LLM Wiki 最重要的不是工具，而是“知识要被编译”的意识。

读资料之后，如果只是存在聊天里，知识会散掉；如果只是存在原文里，每次都要重新理解；如果被整理成 wiki，它就可以被继续链接、修订、调用和生长。

所以后续使用这套方法时，重点不是让 LLM 回答得多漂亮，而是让每一次阅读和提问都留下结构化产物：

- 新资料进入后，要改动相关旧页面。
- 新问题产生好答案后，要沉淀为页面。
- 新结论出现时，要追踪它从哪些来源而来。
- 新矛盾出现时，要显式保留，而不是假装一致。

## 可落地的最小版本

从当前 vault 里可以先用一个很小的版本开始：

1. 每个主题有一个 `index.md`，作为入口。
2. 每次处理资料，都生成来源摘要页。
3. 每次资料进入，都更新相关概念页。
4. 每次重要问答，都判断是否值得写回 wiki。
5. 每隔一段时间，让 LLM 做一次 lint，找孤页、矛盾和缺口。

先不用急着上复杂向量检索。只要 `index.md` 和页面链接维护得好，中小规模知识库已经可以跑起来。

## 关键提醒

> [!important]
> LLM Wiki 的目标不是收藏更多资料，而是让已有资料持续变成可调用的理解。
