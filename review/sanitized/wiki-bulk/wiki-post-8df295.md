## 哈希冲突处理

哈希冲突发生在多个 key 映射到同一槽位时。冲突处理策略会影响查找复杂度、内存局部性、删除成本和并发实现难度。

| 方法 | 核心机制 | 平均查找 | 优点 | 风险与代价 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| 链地址法 | 每个槽位挂链表或桶，冲突 key 追加到同一桶。 | `O(1 + α)`，`α` 为负载因子。 | 实现简单，删除直接，能容忍较高负载。 | 指针追踪导致缓存不友好；桶过长时退化。 | 高冲突、实现简单优先、需要稳定删除语义。 |
| 开放寻址 | 冲突时在线性探测、二次探测等序列中寻找空槽。 | 低负载接近 `O(1)`。 | 数据在数组内，内存紧凑、缓存局部性好。 | 高负载下探测链变长；删除需要 tombstone 或重排。 | 内存敏感、负载因子可控的哈希表。 |
| 双重哈希 | 用第二个哈希函数决定探测步长。 | 接近 `O(1)`。 | 比线性探测更能降低聚集效应。 | 需要选择互补且质量足够的哈希函数。 | 中等负载、希望保留开放寻址局部性的场景。 |
| Cuckoo Hashing | 每个 key 有多个候选槽；插入冲突时踢出旧 key 并重定位。 | 查询通常检查少数槽，接近 `O(1)`。 | 查找路径短，适合读多和缓存场景，可设计并发变体。 | 高负载下可能出现循环重定位，需要扩容或 stash；插入复杂。 | 高性能缓存、并发哈希表、读路径延迟敏感场景。 |
| Hopscotch Hashing | 开放寻址加邻域约束，把 key 尽量维持在 home bucket 附近。 | 接近 `O(1)`。 | 缓存友好，保留较短探测距离。 | 实现复杂，并发控制比链地址法更难。 | 现代 CPU 上追求局部性的高性能哈希表。 |

负载因子：

$$
\alpha = \frac{\text{当前存储的键值对数量}}{\text{哈希表槽位数}}
$$

## Cuckoo Hashing

Cuckoo Hashing 的查询路径短：每个 key 只需要检查由多个哈希函数给出的少数候选位置。插入时如果候选槽已被占用，会把旧 key “踢出”并用旧 key 的另一个候选位置继续重定位。

适合使用 Cuckoo Hashing 的条件：

- 读路径延迟比插入路径简单性更重要。
- 能接受低到中等负载因子，并在重定位失败时扩容或 rehash。
- 需要控制开放寻址探测链过长导致的尾延迟。
- 并发场景中可以围绕 bucket、版本号或原子操作设计细粒度同步。

工程注意事项：

- 负载因子越高，重定位循环和扩容概率越高。
- 哈希函数质量直接影响候选槽分布，常见选择包括 MurmurHash3 等非加密哈希。
- `libcuckoo` 是 C++ 并发 cuckoo hash map 实现；C 项目若要复用，通常需要 C++ 边界封装，而不是直接当作纯 C 库。
- 对“无锁”能力要按具体实现核验：Cuckoo Hashing 适合做并发优化，但并不天然等于无锁。

## 一致性哈希

一致性哈希把 key 和节点都映射到同一个首尾相接的哈希空间中，key 顺时针找到的第一个节点就是负责节点。它解决的是分布式分片在节点数变化时的迁移范围问题：普通 `hash(key) % N` 会在 `N` 变化后大面积重映射，一致性哈希只影响新增或删除节点相邻区间内的 key。

```text
hash ring: 0 ... 2^32-1
keyA ──顺时针──> node1
keyB ──顺时针──> node2
```

核心流程：

1. 把哈希空间抽象为环。
2. 对物理节点或节点名取哈希，得到环上的节点位置。
3. 对 key 取哈希，沿顺时针方向找到第一个节点。
4. 节点增删时，只迁移受相邻区间影响的 key。
5. 用虚拟节点把一个物理节点映射为多个环上位置，缓解数据倾斜。

| 场景 | 价值 | 注意点 |
| --- | --- | --- |
| 分布式缓存 | 扩缩容时减少缓存大面积失效。 | 客户端和服务端必须使用一致的节点列表与哈希函数。 |
| 分布式 KV | 根据 key 定位负责分片，降低迁移成本。 | 仍需要复制、故障转移和 rebalancing 协议。 |
| 负载均衡 | 请求可稳定落到同一后端，同时支持节点变化。 | 热点 key 仍可能压垮单个节点，需要限流或副本读。 |

记忆方式：取模分片是“节点数变了，全局重算”；一致性哈希是“环上局部挪动，只影响一小段”。

## 缓存系统选型

缓存系统选择哈希冲突策略时，可以按负载、并发和内存局部性分层判断：

1. 实现简单、删除频繁、负载不可控：优先链地址法或分桶链地址法。
2. 内存紧凑、负载可控、追求缓存局部性：优先开放寻址或 Hopscotch Hashing。
3. 读路径延迟敏感、可接受复杂插入和扩容：考虑 Cuckoo Hashing。
4. 多线程写入存在死锁风险时，重点不是“换成某个哈希算法”本身，而是明确锁粒度、锁顺序、扩容协议和请求生命周期；哈希策略只能降低冲突概率，不能自动消除所有并发死锁。
